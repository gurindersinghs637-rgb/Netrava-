# NETRAVA Backend API

The FastAPI application exposes version 1 routes under `/api/v1`. The live OpenAPI document is generated by FastAPI at `/api/v1/openapi.json`; Swagger UI is at `/api/v1/docs`.

## Local startup

Run from the repository root with the project Python 3.11 Conda environment:

```powershell
& 'C:\Users\HP\.conda\envs\py311\python.exe' -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

The model loads during startup. `/api/v1/health` reports `degraded` unless the model is loaded and the configured Supabase REST endpoint passes a read-only probe. A missing database configuration is reported as `database_connected: false`.

## Routes

| Method | Path | Access | Purpose |
|---|---|---|---|
| GET | `/api/v1/health` | Public | Model readiness and read-only Supabase connectivity status |
| POST | `/api/v1/auth/login` | Public | Authenticate with Supabase GoTrue and return a token plus trusted profile |
| GET | `/api/v1/auth/me` | Bearer token | Validate the Supabase token and return server-side role and clinic profile |
| POST | `/api/v1/patients` | Technician or ophthalmologist | Create a clinic-scoped patient and audit event |
| GET | `/api/v1/patients` | Authenticated | List patients within the caller's clinic |
| GET | `/api/v1/patients/{patient_id}` | Authenticated | Retrieve patient details only within the caller's clinic |
| POST | `/api/v1/screenings` | Technician or ophthalmologist | Validate fundus upload, run QC, store the image, and save screening records |
| POST | `/api/v1/predict` | Technician or ophthalmologist | Multipart upload, EfficientNet-B3 prediction, and `conv_head` Grad-CAM |
| POST | `/api/v1/screenings/{screening_id}/report` | Ophthalmologist | Save a review and audit event atomically |
| GET | `/api/v1/screenings/{screening_id}/report` | Authenticated | Read the clinic-scoped clinical report |

Protected routes require `Authorization: Bearer <Supabase access token>`. In non-test environments the backend validates the token with Supabase Auth and loads role and clinic membership from `public.user_profiles`; it does not authorize from user-editable JWT metadata. The service-role key is only read by backend code.

`POST /api/v1/screenings` accepts `multipart/form-data` with `patient_id`, `eye` (`OD` or `OS`), and `image`. Upload validation checks JPEG/PNG magic bytes, a 15 MiB limit, and Pillow decoding. Ungradable images return 422. Image storage and database configuration are required before a screening can return success.

`POST /api/v1/predict` accepts `multipart/form-data` with an image and a `retinal_image_id` query parameter. Its response contains five class probabilities, the predicted grade, inference duration, and Grad-CAM output. Without configured database/storage, test-only calls can return `persistence_status: "not_configured"` and a null prediction ID; deployed environments require a clinic database before inference.

## Data and persistence behavior

The migration in `supabase/migrations/202611030001_backend_core.sql` creates clinic-scoped tables, RLS policies, private storage buckets, transactional RPCs, and append-only audit records. It has **not** been applied or tested against a Supabase database. Patient creation, screening creation, prediction writes, and clinician reviews use database RPCs intended to commit the record and its audit event together. Storage upload and database persistence are separate services; the backend performs best-effort object cleanup if screening/prediction persistence fails.

The checked-in `shared/api_contracts/openapi_contract.json` is generated from the FastAPI application. Regenerate it after route/schema changes and keep this document aligned with the live OpenAPI document.

`backend/app/services/report_pdf.py` can generate a PDF from explicitly supplied, validated report data and upload it to the private report bucket. PDF rendering and mocked storage behavior have local tests. It is not yet wired to a public report-download endpoint or live `reports` metadata persistence; the existing live report columns and write RPC definitions need reconciliation first.

## Verification boundary

Local unit tests, a local Uvicorn process, and the bundled model fixtures can verify API behavior and AI inference. They do not verify Supabase credentials, live JWT behavior, schema/RLS execution, storage permissions, or clinical accuracy. See `docs/PROJECT_HANDOFF.md` for the latest exact test results and remaining blockers.

## Authoritative normalized contract update (2026-11-13)

This section supersedes the earlier schema/deployment notes above. The supported
migration is `supabase/migrations/202611130001_normalized_backend.sql`; the legacy
migration is archived outside the migration sequence. See FINAL_BACKEND_READINESS_REPORT.md
for evidence and exact deployment/verification steps.

- Technicians, ophthalmologists and administrators may register patients, create
  screenings and request predictions. Only ophthalmologists and administrators may
  submit reports. All trusted active clinic roles may read their clinic data/PDFs.
- Patient detail adds optional diabetes_type, diabetes_duration_years, latest_hba1c
  and is_insulin_dependent fields. Create-request fields are stored structurally.
- `GET /api/v1/screenings/{screening_id}/report/pdf` is authenticated, returns
  application/pdf with an attachment filename and Cache-Control: no-store. It uses
  persisted report/patient/screening/prediction/probability records. It does not
  create public objects or expose permanent storage URLs.
- Prediction still accepts the same image multipart field and retinal_image_id
  query parameter. Upload bytes must equal the original screening upload (SHA-256).
  A mismatch returns 422 IMAGE_MISMATCH. Historical images without a hash return
  409 IMAGE_REUPLOAD_REQUIRED; create a new screening upload. The response retains
  five probabilities, base64 Grad-CAM and a signed heatmap URL on configured storage.
- Report write/read preserves overall_grade, grade_override, ophthalmologist_notes,
  is_urgent_referral, is_signed_off, timestamps and prediction association. An exact
  repeat of a signed review is idempotent; modifying it returns 409 INVALID_STATE.
  A review requires a persisted prediction. Incomplete historical report metadata
  returns 409 LEGACY_REPORT_INCOMPLETE rather than invented grades/flags.
- Per-clinic duplicate MRN returns 409. Cross-clinic resources return 404. Known
  database validation errors return 422, forbidden clinic staff 403, record-state
  conflicts 409, missing resources 404, and unavailable persistence 503.
- Existing FastAPI HTTP errors retain `{detail: {error, message}}`. Request validation
  retains the existing top-level `{error, message, details}` shape. Do not assume
  every failure uses the same envelope; parse both documented forms. No submitted
  password/token/clinical field values are echoed in validation details.
- Auth validates Supabase tokens online using the public/anon key; trusted active
  role/clinic rows use the service key. Disabled clinics/profiles return 403. Provider
  outages return 503; invalid/expired tokens return 401. No auth architecture change.
- Configure BACKEND_CORS_ORIGINS with the exact Flutter web development origin as
  a JSON list if its port differs from the existing localhost defaults. Native
  mobile requests are not subject to browser CORS.
